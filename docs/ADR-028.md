# ADR-028 — Modular Monolith + DDD Module Ownership & Canonical Structure

## Status

**ACCEPTED / LOCKED**

## Date

2026-09-14

---

## 1. Context

Architecture V4 defines the target architecture for the automation platform.

The project is a production Laravel API that is being evolved incrementally
into an automation platform.

The application must remain:

* one Laravel application
* one deployable unit
* production-safe
* incrementally migratable

The project requires clear ownership for:

```text
Identity
Integrations
Connections
Automation
Execution
```

Previous architecture discussions used conceptual layers such as:

```text
Domain
Application
Infrastructure
```

but did not sufficiently lock their physical location.

This created ambiguity about:

* where new business code belongs
* where migrations belong
* where Eloquent models belong
* where routes belong
* where Google applications belong
* where User belongs
* whether new functionality should be created globally and moved later

This ADR resolves that ambiguity.

---

# 2. Decision

The project adopts a:

```text
Modular Monolith + Domain-Driven Design
```

architecture.

The application remains one Laravel application.

The canonical physical module root is:

```text
app/Modules/
```

The initial modules are:

```text
Identity
Integrations
Connections
Automation
Execution
```

These modules are bounded business areas inside the same Laravel application.

They are not separate services.

---

# 3. Canonical Module Structure

Every module uses the following structure:

```text
app/
└── Modules/
    └── {Module}/
        ├── Core/
        │   ├── Entities/
        │   ├── ValueObjects/
        │   ├── Events/
        │   ├── Exceptions/
        │   └── Repositories/
        │
        ├── Application/
        │   ├── Actions/
        │   ├── DTOs/
        │   └── Services/
        │
        ├── Console/
        │   └── Commands/
        │
        ├── Infrastructure/
        │   ├── Eloquent/
        │   ├── Repositories/
        │   ├── Observers/
        │   ├── Mappers/
        │   ├── Database/
        │   │   ├── Migrations/
        │   │   ├── Factories/
        │   │   └── Seeders/
        │   └── Providers/
        │
        ├── Http/
        │   ├── Controllers/
        │   ├── Requests/
        │   ├── Resources/
        │   ├── Middleware/
        │   └── Routes/
        │
        └── Lang/
            ├── ar/
            └── en/
```

This structure is canonical and locked.

---

# 4. Core Is the DDD Layer

The project intentionally uses:

```text
Core/
```

instead of:

```text
Domain/
```

as the physical name of the DDD/domain layer.

Therefore:

```text
app/Modules/Connections/Core/
```

is the correct location for Connection domain concepts.

There is no requirement to create:

```text
app/Domain/
```

for the new architecture.

---

# 5. Identity Ownership

Identity owns:

* User
* authentication
* authorization
* identity lifecycle
* platform access
* identity-related policies

The existing production:

```text
App\Models\User
```

conceptually belongs to Identity.

However:

* it must not be duplicated
* it must not be moved during Phase 2
* it must not be replaced merely for architectural cleanliness

Legacy migration will happen later through an explicit migration phase.

---

# 6. Integrations Ownership

Integrations owns:

* provider definitions
* application definitions
* integration metadata
* actions
* triggers
* action schemas
* trigger schemas
* required scopes

Google applications belong to Integrations.

Examples:

```text
Gmail
Google Calendar
Google Sheets
Google Drive
Google Docs
Google Analytics
```

They are NOT top-level modules.

---

# 7. Connections Ownership

Connections owns:

* OAuth connections
* external account identity
* credentials
* granted scopes
* token expiration
* connection status
* connection lifecycle
* connection-specific errors

A Connection represents:

```text
one authorized external account
```

identified by:

```text
(user_id, provider, external_account_id)
```

---

# 8. Automation Ownership

Automation owns:

* workflows
* workflow triggers
* workflow steps
* workflow configuration
* workflow validation
* workflow activation/deactivation

Automation references Integrations using stable keys.

Example:

```text
google.gmail
google.sheets
```

Automation does not import Google SDK classes.

---

# 9. Execution Ownership

Execution owns:

* workflow executions
* execution steps
* execution status
* execution errors
* execution history
* retries
* execution timing
* trigger-to-execution ingestion coordination

Execution depends on contracts rather than concrete provider SDKs.

---

# 10. Persistence Ownership

All NEW module-owned persistence code must live inside its owning module.

Migrations:

```text
app/Modules/{Module}/Infrastructure/Database/Migrations/
```

Eloquent models:

```text
app/Modules/{Module}/Infrastructure/Eloquent/
```

Repository implementations:

```text
app/Modules/{Module}/Infrastructure/Repositories/
```

Factories and seeders:

```text
app/Modules/{Module}/Infrastructure/Database/Factories/
app/Modules/{Module}/Infrastructure/Database/Seeders/
```

New module-owned migrations MUST NOT be placed in:

```text
database/migrations/
```

New module-owned Eloquent models MUST NOT be placed in:

```text
app/Models/
```

Existing legacy files may remain where they currently are until their
controlled migration phase.

---

# 11. HTTP Ownership

New module-owned HTTP functionality belongs inside its owning module.

For example:

```text
app/Modules/Connections/Http/Controllers/
app/Modules/Connections/Http/Requests/
app/Modules/Connections/Http/Resources/
app/Modules/Connections/Http/Routes/
```

Actual module route definitions belong under:

```text
Http/Routes/
```

Global Laravel route files may contain only the minimal framework registration
required to load module routes.

Existing legacy routes are not required to move immediately.

---

# 12. Core Dependency Rule

Core must remain framework-independent.

Core MUST NOT import:

```text
Illuminate\
Laravel\
Eloquent
Google SDK
Facebook SDK
GuzzleHttp
Carbon
Symfony\HttpFoundation
```

Core may use:

```text
native PHP
DateTimeImmutable
module-owned interfaces
module-owned entities
module-owned value objects
module-owned events
module-owned exceptions
```

Framework-specific conversion belongs to Infrastructure.

---

# 13. Application Dependency Rule

Application coordinates use cases.

The intended dependency direction is:

```text
HTTP
  ↓
Application
  ↓
Core
```

Application may use infrastructure-provided implementations through
appropriate contracts.

Application MUST NOT contain provider-specific SDK business logic.

---

# 14. Infrastructure Dependency Rule

Infrastructure is the framework/provider boundary.

Infrastructure may depend on:

```text
Laravel
Eloquent
Google SDK
Guzzle
Carbon
```

Infrastructure implements the interfaces required by Core/Application.

Core must never depend on Infrastructure.

---

# 15. New Code Rule

All new functionality MUST be created directly inside its owning module.

Correct:

```text
app/Modules/Connections/...
```

Incorrect:

```text
app/Services/NewConnectionService.php
```

followed by a plan to move it later.

Incorrect:

```text
app/Models/Connection.php
```

when Connection is owned by the Connections module.

Incorrect:

```text
database/migrations/create_connections_table.php
```

for new module-owned persistence.

The architectural boundary exists from the first implementation.

---

# 16. Legacy Code Rule

Existing legacy code may temporarily remain outside modules.

Examples include:

```text
app/Models/User.php
app/Models/FacebookAccount.php
app/Services/*
app/Http/Controllers/Api/*
routes/api.php
database/migrations/*
```

This is transitional.

Legacy code is migrated only through controlled phases.

No large-scale movement is performed merely to make the tree look cleaner.

---

# 17. No Duplicate User Model

The project MUST NOT create:

```text
app/Modules/Identity/Infrastructure/Eloquent/User.php
```

as a second competing production User model while:

```text
app/Models/User.php
```

still owns the same production behavior.

When Identity migration eventually occurs, it must be handled through an
explicit migration plan.

---

# 18. No Google Top-Level Module

The project MUST NOT create:

```text
app/Modules/Google/
```

as a top-level business module.

Google is a Provider.

Its applications are Integrations:

```text
google.gmail
google.calendar
google.sheets
google.drive
google.docs
google.analytics
```

Google-specific infrastructure belongs under the Integrations module's
Infrastructure boundary.

---

# 19. Localization

Every module contains:

```text
Lang/ar/
Lang/en/
```

User-facing messages should be localizable.

No fake translation keys should be created simply to fill directories.

---

# 20. Empty Structure vs Speculative Code

The physical module structure is canonical.

However, canonical folders do not justify speculative business classes.

Do not create:

* empty interfaces
* fake entities
* unused DTOs
* unused repositories
* unused services
* placeholder events
* future-only abstractions

unless the current implementation phase has a real consumer for them.

This preserves ADR-021.

---

# 21. Boundary Interfaces

An interface is allowed with one implementation when it represents a real
architectural boundary.

For example:

```text
Connections/Core/Repositories/ConnectionRepository
```

may have one implementation:

```text
Connections/Infrastructure/Repositories/EloquentConnectionRepository
```

The interface exists because it separates Core/Application from Infrastructure.

Multiple implementations are NOT required before creating a genuine boundary.

---

# 22. Module Isolation

Modules should communicate through:

* application contracts
* domain concepts where explicitly allowed
* stable identifiers
* DTOs
* events
* repository/application interfaces

Modules must not reach into each other's Eloquent internals.

For example, Automation should not directly query:

```text
Connections/Infrastructure/Eloquent/*
```

Instead, it should use an appropriate application/core boundary.

---

# 23. Connections Phase Ownership

Phase 2 is owned by:

```text
Connections
```

Phase 2 introduces the first real module-owned DDD concepts.

Therefore Phase 2 also absorbs the architecture skeleton work that was
previously assigned to Phase 1.

This follows ADR-027.

---

# 25. Connection Persistence

Phase 2 introduces:

```text
connections
oauth_states
```

The new migrations belong to:

```text
app/Modules/Connections/Infrastructure/Database/Migrations/
```

The new Eloquent models belong to:

```text
app/Modules/Connections/Infrastructure/Eloquent/
```

---

# 26. Connection Uniqueness

The database invariant is:

```text
UNIQUE(user_id, provider, external_account_id)
```

This prevents duplicate Connections for the same user's external account.

Multiple Google accounts are allowed because they have different provider
external account IDs.

---

# 27. Connection Credentials

New connection credentials MUST be encrypted at rest.

Credentials include sensitive provider tokens.

They MUST NOT be exposed through:

```text
GET /api/connections
```

or any Connection Resource.

They MUST NOT appear in:

```text
logs
exceptions
API responses
Swagger
debug output
```

---

# 28. OAuth State

OAuth state must be:

* cryptographically random
* bound to user
* bound to provider
* bound to requested scopes
* expiring
* single-use
* replay-protected

Phase 2 uses:

```text
10 minutes
```

as the state expiration period.

Callback consumption must be atomic.

Replay must fail.

---

# 29. Phase 2 OAuth Scopes

The new Connections OAuth flow is separate from platform login.

For the initial Phase 2 connection authorization, the requested Google
identity scopes are:

```text
openid
email
profile
```

Phase 2 does NOT request:

```text
gmail.readonly
gmail.send
calendar.events
spreadsheets
drive
documents
analytics
```

Google API execution is not part of Phase 2.

Integration-specific API scopes are introduced by the appropriate later
integration flow.

---

# 30. Existing Authentication Protection

The existing live Google authentication flow is:

```text
register()
redirect()
callback()
```

Specifically:

```text
GoogleAuthController::redirect()
GoogleAuthController::callback()
```

This flow is protected.

Phase 2 MUST NOT modify:

```text
redirect()
callback()
```

Phase 2 MUST NOT change:

```text
users.google_access_token
users.google_refresh_token
users.google_token_expires_at
```

The new Connections OAuth flow writes only to the new Connections persistence.

---

# 31. Legacy Authentication Exceptions

`redirectgoogle()` is legacy and remains untouched.

`TestLoginController` is development/testing-only and remains untouched.

Facebook remains outside Phase 2.

These are protected boundaries for the current implementation phase.

Phase 2 includes:

```text

OAuthState domain concept
Connection persistence
OAuth state persistence

encrypted credentials
connection list
connection disconnect

```

Phase 2 does NOT include:

```text

workflow engine
execution engine
Integration Catalog implementation
Google API execution
legacy Google token migration
legacy auth refactoring
Facebook migration
Swagger finalization
```

# 33. Migration Principle

The architecture evolves incrementally.

The migration pattern is:

```text
Existing Production Code
        ↓
Characterization / Safety
        ↓
New Module-Owned Boundary
        ↓
Compatibility Layer
        ↓
Gradual Legacy Migration
        ↓
Legacy Removal
```

Never perform a destructive big-bang rewrite.

---

# 34. Architectural Change Control

This ADR is locked.

An implementation phase MUST NOT silently change:

* module ownership
* module names
* canonical module structure
* Core naming
* migration ownership
* Eloquent ownership
* HTTP ownership
* Provider/Integration/Connection terminology
* legacy compatibility rules

If a genuine architectural change is required:

```text
Stop
 ↓
Explain the problem
 ↓
Propose the change
 ↓
Create a new ADR
 ↓
Receive explicit approval
 ↓
Implement
```

No implementation agent may silently override this ADR.

---

# 35. Consequences

### Positive

* Clear ownership of business capabilities.
* New code starts in the correct architectural location.
* Database ownership is explicit.
* Eloquent ownership is explicit.
* HTTP ownership is explicit.
* Google applications are correctly modeled as Integrations.
* User remains owned by Identity.
* DDD Core remains framework-independent.
* Legacy migration remains incremental.
* The project remains a modular monolith.
* No speculative global architecture is required.

### Negative

* The repository temporarily contains legacy global code and new module-owned
  code side by side.
* Some migration phases will require compatibility boundaries.
* The final cleanup will take multiple controlled phases.

These trade-offs are intentional and accepted.

# 37. Final Principle

The project follows this rule:

```text
One application.
Five business modules.
Clear ownership.
Core stays framework-independent.
New code starts inside its owning module.
Persistence belongs to the owning module.
HTTP belongs to the owning module.
Legacy code migrates gradually.
No speculative architecture.
No silent architectural changes.
```

This decision is **ACCEPTED / LOCKED**.
